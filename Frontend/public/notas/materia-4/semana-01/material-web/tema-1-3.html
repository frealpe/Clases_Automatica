Definición — BSP (Board Support Package) El BSP es el conjunto de drivers, bibliotecas HAL (Hardware Abstraction Layer) y archivos de configuración que Nios II EDS genera automáticamente a partir del .sopcinfo: expone a nivel de software exactamente los periféricos, direcciones base e interrupciones del sistema que se armó en Platform Designer. Si el sistema de hardware cambia — se agrega un periférico, cambia una dirección base — el BSP debe regenerarse; de lo contrario el software queda describiendo un sistema que ya no coincide con el bitstream programado en la FPGA.
Compilación cruzada El programa en C se compila en la máquina host con un compilador cruzado (nios2-elf-gcc, parte de Nios II EDS) que genera código máquina para la arquitectura Nios II, no para la máquina host. El ejecutable resultante (.elf) se descarga a la memoria del sistema a través del mismo cable USB-Blaster usado para programar la FPGA, usando el enlace JTAG.
Definición — JTAG UART La JTAG UART es un periférico Avalon-MM que expone un canal serie sobre el mismo cable JTAG usado para programar la FPGA — no necesita un puerto serie físico aparte. Es el mecanismo más simple para que un primer programa en Nios II se comunique con el computador anfitrión: printf en C se enruta, vía el HAL del BSP, a la JTAG UART como salida estándar (stdout), y se lee desde una terminal Nios II en el host.
Cómo encajan las tres piezas El BSP no es un artefacto aislado: es la traducción, a nivel de software, del sistema exacto que se vio en 1.2 generado por Platform Designer. Por eso el .sopcinfo es el hilo conductor de todo el flujo — nace en Platform Designer, y tanto el BSP como la asignación de memoria del programa dependen de él. Cambiar el hardware sin regenerar el BSP es la causa más común de errores de "System ID mismatch" al ejecutar (ver la práctica guiada).
